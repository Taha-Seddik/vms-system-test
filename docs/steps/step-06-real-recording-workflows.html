Real recording workflows

Manual, continuous, and simulated-motion recording now run real FFmpeg processes against the RTSP feeds. Every successful segment is a finalized, FFprobe-validated H.264 MP4 on the persistent Docker volume with matching PostgreSQL metadata and system events.

Completed: 26 July 2026 Engine: FFmpeg Validation: FFprobe Storage: Docker named volume

1. Assessment requirement

Recording cannot be a fake status change. The assessment requires continuous, manual, and event-triggered recording. Motion may be simulated, but that simulation must create a real event and trigger a real playable recording.

Capture

Read the actual camera RTSP stream with FFmpeg and write MP4 media.

Persist

Store lifecycle, ownership, duration, size, failure, and trigger linkage in PostgreSQL.

Prove

Open every completed output with FFprobe before declaring it successful.

2. Completed outcome

  • Manual start and explicit stop with graceful MP4 finalization.
  • Continuous recording as consecutive, independently playable 10-second MP4 segments.
  • Simulated motion creates a Motion Detected event and an automatic eight-second event recording.
  • One active recording mode per camera; conflicts return HTTP 409.
  • Operator/Administrator policy on commands; Viewer receives HTTP 403.
  • Persistent metadata, GUID file names, file size, media duration, owner, and trigger event.
  • Camera REC state and command-center active count update during the process.
  • Recording Started, Stopped, and Failure events update the realtime dashboard.
  • API restart reconciliation marks interrupted rows Failed and clears stale REC state.
  • Failed or header-only outputs are never reported as successful recordings.

Why continuous recording uses segments

A single never-ending MP4 is not safely playable until its metadata is finalized. Short segments create durable playable files continuously and reduce loss if a process stops unexpectedly.

4. Recording lifecycle

  1. The service verifies the camera exists, is enabled and Online, and has no active recording.
  2. PostgreSQL receives a Recording row before process start; camera state changes to Recording.
  3. FFmpeg receives safe argument-list values and copies H.264 from RTSP into a GUID-named MP4.
  4. A stop request gives short captures a six-second minimum window, then sends FFmpeg q to finalize MP4 metadata.
  5. FFprobe must find a video stream and positive duration before the row becomes Completed.
  6. The camera returns to NotRecording and a success or critical failure event is published.

6. Recording dependencies

FFmpeg

Connects to RTSP, copies the H.264 video stream, and finalizes MP4 files. It is installed inside the API image.

FFprobe

Reopens finished files and proves a real video stream and positive media duration exist.

PostgreSQL + volume

PostgreSQL stores searchable metadata; the Docker named volume stores media across container recreation.

No new host installation is required.

Docker builds FFmpeg and FFprobe into the API container. The existing one-command docker compose up --build -d startup remains sufficient.

7. Media and process safety

No shell
FFmpeg arguments are added individually; camera URLs are never interpolated into a shell command.
Safe names
The server creates file names from GUIDs. A user cannot choose a disk path.
Graceful stop
FFmpeg receives q, followed by a timeout and forced kill only if necessary.
Credential safety
RTSP credentials are redacted from persisted failures and logs.
Real validation
FFprobe reads every output; file existence or byte count alone is insufficient.
Persistent volume
recording-data survives normal container recreation and API restart.

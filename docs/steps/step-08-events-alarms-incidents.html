Events, alarms, and incidents

Step 8 turns records created by authentication, camera monitoring, recording, motion, and storage monitoring into one operational workspace. Operators can filter history, inspect every required field, close an event, and see updates without refreshing.

Completed: 26 July 2026 Access: Administrator + Operator Updates: SignalR + 30-second fallback Lifecycle: Open → Closed

1. Assessment requirement

The PDF requires Camera Offline, Motion Detected, Recording Started, Recording Stopped, Storage Full, Camera Reconnected, User Login, and User Logout. Each event needs a timestamp, camera, severity, description, and Open/Closed status. The command center also needs a live event panel, active alarms, and recent incidents.

Assessment interpretation: an incident is an operational event, so this project does not duplicate the same data in a separate incident subsystem. Authentication events remain user activity; every other event type is an incident.

2. Completed outcome

Investigate

The Events page filters the newest records by date, camera, type, severity, and status.

Respond

Selecting a row opens complete details. Closing an Open event removes it from active alarms.

Stay current

SignalR triggers a REST refresh. A 30-second poll remains available if live transport fails.

3. One event model

Every producer writes the existing SystemEvent entity. Step 8 adds StorageFull and exposes two calculated classifications: isActiveAlarm and isIncident.

RecordingFailure remains as an extra event type because recording failures are explicitly required elsewhere in the PDF.

4. How the flow works

1

A real subsystem writes an event

A camera probe fails, a user signs in, motion is simulated, FFmpeg changes state, or disk usage becomes critical.

2

PostgreSQL is authoritative

The event is persisted with its type, UTC time, optional camera, severity, description, and status.

3

SignalR announces a change

The small notification tells connected screens to reload authoritative REST data.

4

The operator responds

Filters narrow history, details explain the record, and Close persists status and publishes another update.

5. Alarm and incident rules

Active alarm

An event is active only when status is Open and severity is Warning or Critical. Closing it makes this false immediately.

Incident

Every event except User Login and User Logout is operational. Login/logout stay classified as user activity.

6. Storage Full is automatic

A background monitor checks real recording-volume metrics every configurable 30 seconds. Critical usage creates one Open Critical Storage Full event; repeated checks cannot duplicate it. Recovery to Healthy or Warning closes the open storage event.

The demo disk is normally healthy, so critical and recovery transitions are verified with a controlled metrics provider in the integration tests. Runtime monitoring reads the mounted filesystem.

10. What you should understand

SignalR is an invalidation signal

It says “something changed”; REST and PostgreSQL remain the source of truth.

Closing is acknowledgement

It changes event status; it does not itself repair a camera or storage device.

System-wide is valid

Login, logout, and storage events do not belong to one camera, so the UI says System-wide.

The API enforces access

Navigation hiding is convenience. Server policy prevents Viewers from reading or closing events.

Executive summary

This step deliberately implements infrastructure rather than VMS business features. Its purpose is to prove that all later work has a stable place to run and a reliable source of video.

What the assessment required

The assessment names Docker deployment as a minimum deliverable and requires multi-camera live monitoring later in the solution. It permits open-source libraries, public APIs, and RTSP sample streams.

Direct Step 1 requirement

  • A Docker-deployable project.
  • A frontend and REST API foundation.
  • Video sources suitable for multi-camera live view.
  • README setup instructions.

Chosen implementation

  • Docker Compose for a one-machine assessment deployment.
  • Four deterministic local feeds instead of unreliable public streams.
  • RTSP ingest and HLS output through MediaMTX.
  • Automated health and media verification.
The stack is our design choice The PDF does not mandate React, ASP.NET Core, PostgreSQL, Material UI, MediaMTX, FFmpeg, SignalR, or Docker Compose. They were selected because they provide a pragmatic, demonstrable implementation within the assessment timebox.

MediaMTX: what it does and how we use it

MediaMTX is the bridge between camera-oriented streaming protocols and browser-oriented playback. Think of it as a media router, not the VMS application or database.

Input

Receives RTSP publishers

Each FFmpeg container publishes to one named path: camera-1 through camera-4. TCP is used for deterministic behavior inside Docker networking.

Output

Produces HLS over HTTP

Browsers cannot normally play RTSP directly. MediaMTX remuxes the same H.264 stream into an HLS playlist and segments without asking the React application to process video.

Observation

Exposes API and metrics

A control API on port 9997 and metrics on 9998 provide media-server visibility. The internal control endpoint is also used for the container health check.

Responsibility

Does not implement RBAC

MediaMTX moves streams. The ASP.NET application remains the authority for user roles, Viewer assignments, and protected application workflows.

Understanding the HLS URL

Camera 1 master playlist HTTP endpoint 
http://localhost:8888/camera-1/index.m3u8

The first playlist is a master playlist. It references a media playlist such as main_stream.m3u8, which in turn references short MPEG-TS segments. FFprobe follows this chain and confirms that the segments contain usable video.

MediaMTX is not our recording subsystem Although MediaMTX has recording capabilities, the approved design uses an application-managed FFmpeg recording service in Step 6. That gives the API explicit lifecycle control and lets it create database metadata, failures, events, and playable MP4 files as one coordinated workflow.

compose.yaml Reusable camera service definition 
x-camera-generator: &camera-generator
  image: vms-camera-generator:local
  build:
    context: ./infra/camera-generator
  depends_on:
    mediamtx:
      condition: service_healthy
  healthcheck:
    test: ["CMD-SHELL", "pidof ffmpeg >/dev/null || exit 1"]

services:
  camera-1:
    <<: *camera-generator
    environment:
      CAMERA_PATH: camera-1
      CAMERA_LABEL: Camera 1 - Entrance

The YAML anchor prevents four nearly identical service definitions from drifting apart. Each camera overrides only identity and color.

Repository structure

The monorepo stays intentionally lean: one backend application, one backend test project, one frontend, infrastructure, scripts, and documentation.

Why there is no large Clean Architecture solution The assessment has a 1–2 day target. Extra application/domain/ infrastructure projects would add ceremony before adding evidence. The API can still maintain clear feature folders and service boundaries as its domain grows.

Important implementation code

These excerpts are intentionally selected from the real source. They show the mechanics that later steps depend on.

1. FFmpeg creates a real encoded camera stream

infra/camera-generator/entrypoint.sh Generated H.264 RTSP publisher 
ffmpeg \
  -re \
  -f lavfi \
  -i "testsrc2=size=${CAMERA_RESOLUTION}:rate=${CAMERA_FPS}" \
  -vf "hue=h=${CAMERA_HUE},drawtext=...:text='${CAMERA_LABEL}'" \
  -c:v libx264 \
  -preset ultrafast \
  -tune zerolatency \
  -pix_fmt yuv420p \
  -g "$GOP_SIZE" \
  -b:v 500k \
  -rtsp_transport tcp \
  -f rtsp \
  "$PUBLISH_URL"

-re publishes at real-time speed. testsrc2 generates moving video. H.264 with yuv420p is broadly compatible. A two-second GOP aligns regular keyframes with the two-second HLS segment target. The publisher runs in a retry loop so a MediaMTX restart is recoverable.

2. The API exposes a health contract

backend/Vms.Api/Program.cs HTTP liveness and container self-probe 
app.MapGet("/health", () => Results.Ok(new
{
    status = "Healthy",
    service = "vms-api",
    timestamp = DateTimeOffset.UtcNow
}));

The API also accepts a --health-check command argument. Docker starts a short-lived copy of the application assembly with that argument; it calls the already-running API and returns process exit code 0 or 1. This avoids adding Curl to the production image.

4. Verification checks media—not only HTTP

scripts/verify-foundation.ps1 Playlist parsing and FFprobe 
$playlistContent = if ($playlist.Content -is [byte[]]) {
    [System.Text.Encoding]::UTF8.GetString($playlist.Content)
}
else {
    [string]$playlist.Content
}

if ($playlistContent -notmatch "#EXTM3U") {
    throw "$cameraPath returned a response, but it is not an HLS playlist."
}

docker compose exec -T camera-1 ffprobe `
  -select_streams "v:0" `
  -show_entries "stream=codec_name,width,height,r_frame_rate" `
  -of json `
  "http://mediamtx:8888/$cameraPath/index.m3u8"

An HTTP 200 response could still contain an error page. The script therefore validates the HLS signature and then asks FFprobe to open and decode stream metadata. The byte-array branch exists because Windows PowerShell returns the HLS MIME type as binary content.

What to understand before Step 2

Step 2 adds the first real application security boundary. These points guide that implementation.

  1. The API—not the frontend—is the authority.
    Hiding a button or route in React improves UX but does not secure data. Every restricted API operation must enforce role and assignment rules on the server.
  2. Viewer camera assignments are mandatory data.
    The PDF says Viewers may see assigned live cameras only. Step 2 therefore needs a many-to-many user/camera authorization model, even though full camera CRUD arrives in Step 3.
  3. Media access and application authorization are separate.
    A user should receive a camera or stream reference only after the API authorizes them. Direct local HLS remains a development boundary until protected media delivery is completed.
  4. User activity begins with authentication.
    Successful login, logout, and recent authenticated requests will later contribute to User Login/User Logout events, active-user metrics, and operator activity.
  5. PostgreSQL becomes active application infrastructure.
    Step 2 introduces database migrations and durable users, roles, assignments, and activity state. The existing database health gate ensures the API starts after PostgreSQL is ready.
  6. Generated feeds remain stable test fixtures.
    They should not be replaced while security is being built. Stable camera identifiers make authorization tests deterministic.
Step 1 exit condition is satisfied The repository and media foundation are ready. Step 2 may begin only after the user explicitly approves this gate.

Small glossary

RTSP
A streaming control protocol commonly exposed by IP cameras. It is useful for ingest but is not natively playable by normal browsers.
HLS
HTTP Live Streaming. A playlist plus short media segments that can be transported through normal HTTP infrastructure and played with HLS.js or native browser support.
Remux
Repackages already encoded media into another container/protocol without decoding and re-encoding every frame.
H.264
The video codec used by the generated feeds. It provides broad compatibility for RTSP, HLS, MP4, browsers, and FFmpeg workflows.
GOP
Group of Pictures: the distance between keyframes. Regular keyframes help HLS segmenting, seeking, snapshots, and future recording keyframe extraction.
FFprobe
FFmpeg’s inspection tool. It validates that a URL contains actual, decodable media and reports codec, resolution, and frame rate.
Health check
A repeatable probe used by Docker to determine whether a service is ready, rather than merely whether its process exists.
Named volume
Docker-managed persistent storage. PostgreSQL data survives ordinary docker compose down and container rebuilds.

Authentication, roles, and camera assignments

Step 2 creates the application's identity boundary: securely hashed credentials, signed and revocable JWT sessions, three assessment roles, server-side Viewer camera filtering, protected React routes, and persisted login/logout activity.

Completed: 26 July 2026 Backend: ASP.NET Core + EF Core Database: PostgreSQL migration Frontend: React Router + Material UI

1. Assessment requirement

The assessment requires login-based access for Administrator, Operator, and Viewer users. Authorization must apply to API and frontend behavior, and a Viewer must see only cameras explicitly assigned to that account. Login, logout, and ongoing user activity must also be recorded.

Authenticate

Validate credentials without storing plaintext passwords and issue an access token that identifies the user and role.

Authorize

Enforce Administrator, Operator, and Viewer permissions on the server and present only appropriate frontend navigation.

Assign

Persist Viewer-to-camera assignments and filter accessible cameras at the API boundary, not merely with hidden UI.

3. Authentication flow

A JWT proves that the API created a token, while the persisted session proves that the token is still allowed. This extra lookup makes logout effective immediately instead of waiting for expiry.

1. Login Username + password over HTTP in the local stack
→
2. API verifies PBKDF2 hash + account + Viewer assignment
→
3. Session + JWT Database session ID becomes the token JTI
→
4. Every request Signature, expiry, role, session, and enabled user checked

Why use both JWT and a session row?

A purely stateless JWT remains valid after logout. The session row allows the API to reject a revoked token immediately and supports active-user and activity metrics required by later dashboard work.

4. Backend and database design

The API uses explicit, discoverable layers. Controllers translate HTTP requests and responses, services contain workflows and business decisions, models define transport/configuration shapes, domain holds entities and enums, extensions compose framework registration, and data owns EF Core persistence. 

Vms.Api/
├── Controllers/   Auth, cameras, access-policy, and system HTTP APIs
├── Services/      Authentication, JWT, session, and camera-access logic
├── Models/        Requests, responses, camera DTOs, and JWT options
├── Domain/
│   └── Entities/  Users, sessions, assignments, and system events
├── Extensions/    DI, JWT setup, policies, claims, and persistence setup
├── Utils/         Small reusable stateless helpers
├── Data/          DbContext, migrations, initialization, and demo IDs
└── Program.cs     Middleware pipeline and controller mapping only

Users

Stores normalized unique usernames, display names, password hashes, role, enabled state, creation time, last login, and last activity.

UserSessions

Stores token/session identity, expiry, recent activity, and optional revocation time and reason.

UserCameraAssignments

Uses a composite key of user ID and camera ID so the same camera cannot be assigned twice to one Viewer.

SystemEvents

Records typed login/logout events with timestamp, severity, status, user, camera reference, and description fields that can expand during Step 8.

Endpoint Access Purpose
POST /api/auth/login Anonymous Verify credentials and create a JWT session.
POST /api/auth/logout Authenticated Revoke the current session and write a logout event.
GET /api/auth/me Authenticated Return the current enabled user and assignments.
GET /api/auth/activity Administrator Return active sessions and recent identity events.
GET /api/cameras/accessible Authenticated Return all cameras or the Viewer's assigned subset.

5. Role and assignment rules

Role Camera scope Step 2 UI/API access
Administrator All four demo cameras Cameras, Administrator policy, and activity page
Operator All four demo cameras Cameras and operational policy; no activity page
Viewer Only camera-1 and camera-2 Cameras only; rejected by Operator/Admin policies

Mandatory assignment invariant

A Viewer with zero assignments cannot sign in. Once signed in, camera IDs are loaded from PostgreSQL and intersected with the known camera catalog. The frontend never decides the Viewer's camera scope.

6. Frontend authorization

React stores the assessment session in browser sessionStorage, validates it with /api/auth/me on startup, attaches the Bearer token to API requests, and clears local state even if logout fails.

Protected routes

Anonymous visitors are redirected to login. A nested role guard redirects non-Administrators away from the activity page.

Role-aware navigation

Every user sees accessible cameras. Only Administrators receive the Activity navigation link.

Assessment accounts

Login provides selectable local demo credentials for all three roles, making the permission differences quick to review.

Visible scope

The camera page explains the current role and shows only the camera records returned by the authenticated endpoint.

var assignedIds = await database.UserCameraAssignments
    .Where(item => item.UserId == userId)

10. Boundaries and what comes next

Intentional Step 2 boundaries

Camera records remain the four static foundation entries until Step 3 adds camera/group CRUD and health. HLS playback remains outside the UI until Step 5. MediaMTX's raw HLS port is still a local development endpoint; final media URL protection and secret hardening are explicitly scheduled for Step 10. Session storage is a pragmatic assessment choice and requires normal XSS prevention.

Before proceeding to Step 3, understand:

  • The API, not React, is the authority for roles and assignments.
  • A JWT is accepted only while its PostgreSQL session remains active.
  • Viewer assignment records already use stable camera string IDs.
  • Step 3 must replace the static catalog without weakening the same filter.
  • Login/logout events are intentionally the first members of the future event model.
